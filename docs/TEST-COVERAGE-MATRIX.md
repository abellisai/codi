# Matrice dei comportamenti coperti

Documento richiesto da §20.4 e da §21.2: elenca i **comportamenti osservabili** che hanno un test
scritto, con l'area, il livello, il file che li prova e la sezione normativa. Non è un elenco di
test né un punteggio: un test scritto non è un test superato, e i numeri di copertura vivono in
`scripts/coverage-baseline.json`.

Aggiornato: 13 novembre 2026, dopo la correzione della raccolta di copertura.
Riferimento: [specifica
tecnica](../SPECIFICA_TECNICA_PIATTAFORMA_DIDATTICA.md) §20.3–§20.4.

- Una riga descrive un comportamento esterno, non un dettaglio privato: se il comportamento
  sparisce, il test che lo documenta deve fallire.
- Il livello dichiarato è quello del `Trait("Category", …)` nel file. Dove il file non dichiara
  alcun `Trait`, la riga è marcata **DA VALIDARE**: il livello è deducibile dalla lettura, non
  dichiarato dall'autore, quindi non si presenta come verificato.
- La matrice va aggiornata quando cambia un comportamento di produzione o il suo test (§20.4). Un
  requisito implementato e già descritto non aggiunge versioni della specifica: aggiorna questa
  matrice e lo stato.

### Misura precedente — seconda porzione di T2

Per la seconda porzione di T2 (organizzazione: classi, corsi e associazioni) l'agente ha eseguito
build Release (0 errori, 0 warning) e **373 test .NET su 373**: 134 nel progetto Domain.Tests e
239 nel progetto IntegrationTests. La raccolta di copertura è in
`TestResults/1edabefb4e344ddd911711bf3da955a8`, con tre report Cobertura.
Il gate passa **contro la baseline esistente**. Il primo giro era rosso sull'assembly
`Application` (93,47%): i percorsi di errore dei nuovi comandi — versione mancante o obsoleta,
validazione del titolo e della descrizione, modifica senza cambiamenti, archiviazione ripetuta —
non erano coperti. Sono stati aggiunti come test, non neutralizzati abbassando la soglia.
Restano scoperte soltanto le righe difensive non raggiungibili senza concorrenza reale, come il
conflitto fra l'aggiornamento condizionato e la verifica di versione già superata.
I controlli frontend (49 test, lint, formattazione, build di produzione e audit di runtime)
sono stati eseguiti nella stessa verifica.

[test-coverage-gate.ps1](../scripts/test-coverage-gate.ps1) verifica quattro regressioni su
report sintetici: righe omonime in file diversi, unione della stessa riga fra report,
assembly previsto ma assente, calo effettivo. Esito: **4/4** su PowerShell 7 e Windows
PowerShell 5.1; lo script si esegue localmente.

### Motivazione dell'aggiornamento della baseline — 30 settembre 2026

La misura precedente univa le righe usando il solo numero, senza file sorgente. Una riga coperta
in un file poteva coprire artificialmente quelle omonime negli altri. La baseline presente
all'inizio della correzione era API 73,27%, Application 98,55%, Domain 99,00%, Infrastructure
99,03%; il dominio falliva già il vecchio gate (misura 94,84%). Questi valori non sono una misura
confrontabile con il calcolo corretto: si rigenera la baseline per ripristinare il significato
del guardrail, non per mascherare una regressione funzionale. Nessun test è stato rimosso e non
sono stati aggiunti filtri o esclusioni di codice. I nuovi test HTTP spiegano l'aumento della
copertura dell'API; quelli di concorrenza verificano perdita dei tentativi, blocco sopraggiunto
e conflitto persistente. Restano scoperti rami di validazione e della modalità CLI: la copertura
non dimostra da sola tutti i flussi.

Comando di rigenerazione:

```powershell
.\scripts\assert-dotnet-coverage.ps1 -ResultsDirectory .\TestResults\fixes-20260930-final -UpdateBaseline
```

Per raccolte successive:

```powershell
$coverageRun = Join-Path .\TestResults ([Guid]::NewGuid().ToString('N'))
dotnet test .\Qwerty.Codi.slnx --configuration Release --no-build `
  --collect:"XPlat Code Coverage" --settings .\coverlet.runsettings `
  --results-directory $coverageRun
.\scripts\test-coverage-gate.ps1
.\scripts\assert-dotnet-coverage.ps1 -ResultsDirectory $coverageRun
```

Ogni aggiornamento futuro richiede una motivazione documentata prima di `-UpdateBaseline`.
Non aggiungere asserzioni vuote né escludere codice scritto a mano per alzare i numeri (§20.4).
